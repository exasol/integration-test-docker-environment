***************
Developer Guide
***************

In this developer guide we explain how you can build this project.

Install Poetry:

``sudo apt install python3-poetry``

Install dependencies:
``poetry install``

Install the Git commit hooks:

``poetry run -- pre-commit install``

.. toctree::
   :maxdepth: 1


Creating a Standalone Executable
********************************
A standalone executable for linux environment can be created as follows. It will be created under ``dist`` folder.

.. code-block:: shell

   poetry run -- nox -s build-standalone-binary -- --executable-name "itde_linux_x86-64"


Creating a Release
*******************

Prerequisites
-------------

* Change log needs to be up to date
* ``unreleased`` change log version needs to be up-to-date
* Release tag needs to match package

  For Example:
        * Tag: 0.4.0
        * \`poetry version -s\`: 0.4.0

Preparing the Release
----------------------
Run the following nox task in order to prepare the changelog.

    .. code-block:: shell

        nox -s release:prepare

Triggering the Release
----------------------
In order to trigger a release a new tag must be pushed to Github.


#. Create a local tag with the appropriate version number

    .. code-block:: shell

        git tag x.y.z

#. Push the tag to Github

    .. code-block:: shell

        git push origin x.y.z

What to do if the release failed?
---------------------------------

The release failed during pre-release checks
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

#. Delete the local tag

    .. code-block:: shell

        git tag -d x.y.z

#. Delete the remote tag

    .. code-block:: shell

        git push --delete origin x.y.z

#. Fix the issue(s) which lead to the failing checks
#. Start the release process from the beginning


One of the release steps failed (Partial Release)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
#. Check the Github action/workflow to see which steps failed
#. Finish or redo the failed release steps manually

.. note:: Example

    **Scenario**: Publishing of the release on Github was successfully but during the PyPi release, the upload step got interrupted.

    **Solution**: Manually push the package to PyPi

Running Tests
*************

You can execute all tests in a single file with the following command:

.. code-block:: shell

  poetry run -- python exasol_integration_test_docker_environment/test/test_cli_test_environment_db_mem_size.py

Some tests will use prebuilt Docker Containers.
After changing the implementation you might need to rebuild the container in order to make
your changes effective when executing the tests.


Running Integration Tests Locally on Linux
------------------------------------------

Run integration tests on the machine that owns the Docker daemon. Before
starting, install the Poetry dependencies and confirm that the current user can
reach Docker without ``sudo``:

.. code-block:: shell

   poetry install
   docker info

To run a specific test while working on it, use pytest directly. This starts a
disposable Docker-DB environment and removes it when the test finishes:

.. code-block:: shell

   poetry run -- pytest -xvv test/integration/confd_access/test_published_json_rpc_token.py

Use the CI-equivalent Nox session for a generated matrix target. The target
must be one of the values generated by ``matrix:generate``; ConfD tests are
batched targets, not individually supplied file paths:

.. code-block:: shell

   poetry run -- nox -s matrix:generate -- db_versions_integration_test_matrix
   poetry run -- nox -s run-integration-tests -- \
       --db-version=default --test-target='<generated target>'

Direct-container-IP scenarios require the process running pytest to have a
route to Docker's private bridge network. Native Linux Docker normally has this
route. When Docker runs in a Lima VM, execute pytest *inside the VM* instead of
from the host; the project workspace is mounted there and the VM owns the
Docker bridge:

.. code-block:: shell

   limactl shell itde -- bash -lc '\
       cd /home/mykhailo.skliar/github/exasol/integration-test-docker-environment && \
       .venv/bin/pytest -xvv test/integration/confd_access/test_container_ip_json_rpc_token.py'

Replace the path with your checkout path. Do not diagnose a host-side timeout
to a container private IP as a ConfD authentication failure: use a forwarded
ConfD port, an SSH tunnel, or run the direct-IP test on the Docker host.


Configuring Tests
-----------------

ITDE supports tests with pytest although there currently are also tests using
``python.unittest`` mainly in directory
``exasol_integration_test_docker_environment/test``.  The plan is to migrate
all tests to pytest in directory ``test``

For pytest ITDE uses a pytest plugin in directory ``pytest_itde``. This plugin
enables to configure test execution, e.g. setting the hostname, user and
password of the database. For some configuration parameters there are also
default values.


Integration-Test CI Matrix Limit
--------------------------------

GitHub Actions permits at most 256 jobs in one matrix. The integration-test
workflows expand every test target across supported Python or database versions,
so adding a target can exceed that limit. ITDE validates the generated matrix
before it is passed to GitHub Actions and fails with an actionable error instead
of leaving a workflow queued.

Tests in ``test/integration/confd_access`` are batched into 6 matrix targets.
Add a new ConfD test as a ``test_*.py`` file in that directory; it will be added
to an existing batch and will not increase the number of parallel CI jobs. For a
test in another integration-test location, run the matrix generation locally:

.. code-block:: shell

   poetry run -- nox -s matrix:generate -- slow_python_test_matrix db_versions_integration_test_matrix

If the command reports that the matrix is too large, batch related test files by
extending ``_INTEGRATION_TEST_FILE_GROUPS`` in ``noxconfig.py`` or reduce a
matrix dimension. Do not remove the matrix-size validation or add an unbatched
integration-test target while the matrix remains at this limit: one unbatched
target consumes the final slot, and the next makes the workflow invalid.
Keeping the validation produces this actionable error before GitHub Actions
attempts to schedule an oversized matrix.
